## 4. Hallazgo crítico: `userId_startDate` deja de existir como unique compuesto de Prisma Client

Al quitar `@@unique([userId, startDate])` de `mealPlan.prisma` (sección 2.3), Prisma Client deja de generar el input compuesto `MealPlanUserIdStartDateCompoundUniqueInput` (confirmado hoy en `apps/api/src/generated/prisma/models/MealPlan.ts:210` y `:221`, generado a partir del `@@unique` actual). Esto **rompe en tiempo de compilación** los tres call sites reales que hoy usan `where: { userId_startDate: {...} }`:

1. `apps/api/src/modules/plans/plans.repository.ts:16-19` — `findPlanByWeek` usa `findUnique({ where: { userId_startDate: { userId, startDate: weekStart } }, include: {...} })`. **Debe reescribirse** como `findFirst({ where: { userId, startDate: weekStart, isCurrent: true }, include: {...mismo include...} })`, exactamente lo que pide Flujo E del design.md.
2. `apps/api/src/modules/plans/plans.repository.ts:32-37` — `checkPlanExists` usa el mismo `findUnique({ where: { userId_startDate: {...} } })`. **Debe reescribirse** para reflejar "existe una versión actual": `findFirst({ where: { userId, startDate: weekStart, isCurrent: true }, select: { id: true } })`.
3. `apps/api/prisma/seed.ts:134-147` — `prisma.mealPlan.upsert({ where: { userId_startDate: { userId: user.id, startDate } }, update: { endDate }, create: { userId: user.id, startDate, endDate } })`. **Debe reescribirse** sin `upsert` (que exige una unicidad real), con un patrón manual `findFirst` + `create`/`update` condicional (ver sección 6).

Ninguno de estos tres cambios es opcional: sin ellos el build de `apps/api` falla después de regenerar el Prisma Client (fuera de esta sesión, commit 2), y `seed.ts` deja de ejecutar. Documentar esto explícitamente para el tester/implementer porque el design.md sólo menciona el cambio de criterio de búsqueda para `GET /meal-plans/current` (Flujo E) sin mencionar que rompe `checkPlanExists` y el seed.

## 7. ¿Repositorio/servicio nuevo para `GenerationRun`?

**Decisión: no crear módulo nuevo.** Agregar los métodos de la sección 5 directamente a `PlansRepository` (`plans.repository.ts`) y la orquestación de la sección 6 directamente a `PlansService` (`plans.service.ts`), dentro del `PlansModule` ya existente (`apps/api/src/modules/plans/plans.module.ts:10-16`, que ya declara `providers: [PlansService, GeminiService, PlansRepository]`).

Justificación con estructura real del repo:
- El único caller real de `GenerationRun` en esta iteración es el módulo `plans` (sección 1). No hay ningún ticket ni código hoy que necesite leer/escribir `GenerationRun` desde otro módulo.
- Grep confirma que `PlansRepository`/`PlansService`/`PlansModule` **no se importan hoy desde ningún otro módulo** (`apps/api/src/app.module.ts` es el único importador externo, como registro de módulo raíz) — no hay precedente de compartir un repositorio entre módulos en este repo.
- El patrón real más cercano es `IngredientRepository.isIngredientInUse` (`apps/api/src/modules/ingredient/ingredient.repository.ts:52-59`), un método de query específico agregado directamente al repositorio de su propio módulo (no extraído a un módulo/repositorio compartido), a pesar de que consulta una tabla (`recipes`) que no es la entidad principal de ese módulo. `RecipeRepository` (`apps/api/src/modules/recipe/recipe.repository.ts`) también permanece autocontenido dentro de su propio módulo. Ninguno de los dos ejemplos usa un repositorio compartido entre módulos.
- Si en un ticket futuro se conectan `RECIPE_SINGLE`/`RECIPE_BATCH`/`MEAL_REPLACEMENT` (fuera de alcance aquí, design.md sección 8) y el archivo `plans.repository.ts`/`plans.service.ts` crece demasiado, la extracción a archivos hermanos dentro del mismo módulo (p. ej. `apps/api/src/modules/plans/generation-run.repository.ts`, agregado a los `providers` de `plans.module.ts:13`) es una opción de refactor de ese ticket futuro — no de este.

## 8. DTOs

**Confirmado: no hace falta ningún DTO nuevo ni cambio de forma de DTO existente.**

- Contrato de request: `GenerateMealPlanDto` (`apps/api/src/modules/plans/dto/generate-meal-plan.dto.ts:3-7`, sólo `weekStart`) y `CreateMealPlanDto` (`apps/api/src/modules/plans/dto/create-meal-plan.dto.ts:5-17`, `weekStart` + `days`) no necesitan campos nuevos — `idempotencyKeyHash` se calcula server-side (design.md ADR decisión 2), consistente con que la usuaria de este repo es frontend-only y no se introduce contrato nuevo de cliente.
- Contrato de response: `GET /meal-plans/current` (`plans.controller.ts:25-29`) devuelve directamente lo que `PlansService.getPlanByWeek` resuelve (`plans.service.ts:109-115`), que a su vez es el objeto crudo de `PlansRepository.findPlanByWeek` (`plans.repository.ts:16-30`) — no existe ningún DTO de salida en `apps/api/src/modules/plans/dto/index.ts:1-7` (sólo exporta los 6 DTOs de entrada/anidados: `generate-meal-plan`, `meal-plan-query`, `create-meal-plan`, `meal-plan-day`, `meal`, `recipe`, más `nutritional-values`).
